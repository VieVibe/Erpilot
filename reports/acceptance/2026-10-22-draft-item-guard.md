# 草稿商品变更核验：工程验收

日期：2026-10-22。继续多轮订单可靠性主线，功能边界见[契约](../../docs/draft-item-constraints.md)。

## 解决的问题

旧应用会核对客户、备注和预算，但数量工具只校验行号 / SKU，完整修改工具没有核对商品变更的用户依据。
已有成功测试中，用户只说“清空备注”，模型同时把商品 A 从 2 件改为 3 件也被接受。
另一个风险是刷新报价或改预算时，模型顺便减量、删行或替换商品，生成新的可审批版本。

现在，已有草稿的商品参数必须与本轮支持的明确要求及实际读取的版本一致。
错误件数、错误目标、遗漏要求和夹带变更均在保存前拒绝，不新增错误草稿版本，也不改变库存。
支持明确数量修改与末尾追加；其他商品和顺序保持。

## 实现

- 应用从最近真实用户消息解析有限的 SKU / 行号 / 正整数数量要求，隔离备注、普通引文和代码。
  已识别的否定、条件、只读、待确认、可选数量及互相冲突的要求先澄清，不取其中一个子句执行。
- 对完整明细计算允许结果，再按领域 SKU 规范化及合并口径核对模型参数，不自动修改参数。
- 独立 `item_guard` 记录草稿、读取版本、有序前后明细和原话；模型工具参数不能提交该记录。
  领域层在保存事务内复核真实前后快照和逐项授权，随版本写入历史。
- 原预算十阶段流程的明确追加商品保留；报价刷新仍可重新计价。客户 / 备注来源、
  预算、指定版本审批、会话隔离和建单幂等继续沿用。

| 离线业务演示 | **10/10**，所有场景断言通过；[原始结果](20261022-draft-item-guard-demo.json) |
| 静态检查 | Ruff 和差异空白检查通过 |

两条正式 LangGraphRuntime 纠错测试分别使用会话工厂与 MCP 桥：先查询真实当前草稿，
模型提出 6 件而用户要求 5 件，检查其被拒绝且全部表不变；随后纠正为 5 件，
只保存 v2，并核对历史中的原话、前后明细和版本。脚本模型不代表供应商模型准确率。

拒绝路径逐表核对业务状态，覆盖错误目标 / 数量、附带改行、删行 / 重排、预算变更偷减量、
引文 / 历史 / 助手指令、否定追加、待确认条件、多个可选数量、矛盾保留、部分未解析要求，
以及错误新增 SKU / 数量 / 位置。追加错误 SKU 使用实际存在的商品，避免仅靠“商品不存在”通过测试。

领域测试单独覆盖伪造记录、前后快照和版本不符、缺少逐项授权、异常类型、来源引用不符、
新实例恢复历史，以及旧记录与手工表单兼容。

十个演示覆盖报价、库存批准 / 拒绝 / 错误恢复、草稿修改及建单批准 / 拒绝、政策命中 / 无命中、
取消资格与补货建议；使用脚本模型、关键词演示向量、临时 ERP。
它们经过正式应用链路，仍属于离线工程验证。

## 回归处理与范围

初次全仓发现四处兼容问题后修复并继续验证：原预算流程的追加商品需要明确支持；
大响应上下文例使用无“件”单位的明确整数，现保留；两处故障测试以前要求“先写错再由判分发现”，
现要求在写入前得到 `argument_constraint`，逐表 / 摘要相等且任务仍失败并停止后续轮次。
原用例金标、评测评分器、清单哈希和历史真实报告没有改动。
另将旧“只改备注 / 客户”的成功单测改为保持商品数量，错误附带减量由新拒绝测试覆盖。

后续审查补上普通 / 嵌套引文、否定 / 待确认 / 可选数量、冲突保留和否定追加的拒绝路径。
中间成功全仓为 1291 passed / 21 skipped，见[中间 JUnit](20261022-draft-item-guard-interim-tests.xml)；
新增用例与最后规则统一后另跑最终全仓，不将两次通过数相加。

本批没有新增付费模型或嵌入请求，没有部署或迁移实际业务数据库。
21 项跳过依赖显式配置的隔离 PostgreSQL；本轮运行时恢复使用内存检查点，
不代替原硬崩溃矩阵的独立 PostgreSQL 验证。
真实模型仍保留旧批次结果；本轮不代表新的 GLM / DeepSeek 验收。
本机可信单用户、单 API 进程范围不变；创建草稿的商品语义仍未核验，
`items` 继续标记未全面核验，原始 MCP / 可信 Python 与表单的边界见功能契约。

复核清单见[证据及源码哈希](20261022-draft-item-guard-evidence.json)。

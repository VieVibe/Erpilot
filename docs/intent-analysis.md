## 使用

API 的真实 ERP 工具源使用 `ERPILOT_INTENT_MODE=off|shadow|enforce`，默认 `off`。
也可在 `SessionErpTools.create(path, intent_mode="enforce")` 显式注入。
修改环境设置后重启 API；普通 `.env` 和用户数据库未在本批改动。

- `off`：原有工具、参数校验和来源契约。
- `shadow`：调用旧参数校验，共享规则的 `intent_shadow` 结果同时进入本地诊断；无新增元数据表、供应商请求或新执行行为。
- `enforce`：仅在订单草稿工具接入新规则和 SQLite 待完成请求；审批仍走原流程。

例如先说“给客户甲准备订单：标准耳机两件；备注原文『不要提交』；预算不超过1000元；只保存草稿”。
若真实目录重名，程序按固定顺序展示候选。回复“选第二个，其他照旧”，应用恢复原完整要求，
重新核对目录后只保存草稿。多个重名项逐项提问；同轮重复调用解析工具不会回答下一个问题。

编号后可以追加明确修改，例如“选第二个，数量改成四件，预算改为1500元，备注写『预算改为9999元』”。
数量指向本次选中的商品，也可明确原清单中的 SKU；客户支持明确改名，备注和预算支持设置或清空，未提及的字段保持。
多项选择中间的标量修改会保留，直到完整清单核对后一次保存。每条回复的所有增量必须同时通过；
有未知片段、冲突、条件或不支持的增删商品要求时，原待选问题和状态版本保持，不能先消费编号或保存部分结果。

已持久化的待完成请求也支持独立回复“预算改为1500元”“客户改为客户乙，清空备注”，
原候选问题保持，后续继续选择即可。可直接回复展示过的“SKU R2”补商品槽；不接受候选集合之外的 SKU。
完整商品已绑定但保存因库存等原因失败时，可直接说“数量改为四件”修正单商品请求；多商品必须明确 SKU。
这些补充仍要完整重放全部消息并通过保存事务，不会先生成部分清单或自动改库存。

初始请求保留明确客户和完整商品名/SKU，但漏了件数时，也可保存为待完成请求。
例如“给客户甲准备订单：标准耳机，机械键盘；预算不超过1000元；只保存草稿”，
先解决第一项重名，再逐项询问最终件数。可以分别回复“选第二个”“三件”“四件”，
也可将同一项的选择和件数合并为“选第二个，三件，预算改为1500元”。
“机械键盘 3”“机械键盘两箱”“SKU K1 两包”不会按默认单位或包装比例转换，
必须补充明确的总件数，例如“四件”。商品名本身与单位后缀有多个真实解释时，需重新提供明确 SKU。
补问期间回复“三箱”“2包”等包装数量时继续保留原请求并澄清；同轮附带的预算等修改也不先应用。
只处理当前实际展示的问题，不从编号猜件数；没有有效待完成请求时，裸“四件”不会变成对已有草稿的修改。

业务面板新增“核对完整请求”。可以一次检查或编辑客户、全部商品 SKU/件数、备注及预算，也可显式增删和替换行。
未选择商品或缺件数的行保持空白，不自动取第一个候选或填 1；重名项提供实际候选，同时允许明确输入 SKU。
同一请求版本连续两次未能补齐时，面板内自动打开核对窗口；手机先打开业务面板即可使用。
关闭窗口、页面恢复和读取都不保存。保存按钮确认的是表单中全部字段，创建新草稿并重新报价，不申请建单审批。
备注/预算留空明确表示清空/未设置，重复 SKU 和残缺行无法确认；仍需在草稿中核对实际报价及提交条件。

会话中另有已保存草稿时，独立字段回复需要先明确范围：修改待完成请求可说“待完成请求：预算改为1500元”；
如需修改已保存草稿，先撤回待完成请求，再按原草稿流程操作。字段值中的“请提交订单”等文字不授予其他修改、预览或审批权限。
最新已消费请求的完全相同补充原话，在原请求有效期内只读结束，不会自动成为已保存草稿的新版本修改。
显式开始新请求会切换上下文；补充不会延长原请求有效期。

“不要提交，只把当前版本第二行改成三件，预算改为3500元，其他不变”必须完整传入
`revise_order_draft` 一次保存；数量专用工具会拒绝这种部分修改。

已有草稿的“刚才展示的第二个”按实际工具展示的旧版本 SKU 定位，即使它已经移到当前第一行。
“当前版本第二行”只按本轮当前顺序定位。“第二个”没有限定版本时，需要已有真实展示，且新旧行号对应的 SKU 一致；
不一致会显示两种对应关系并澄清整次修改。助手普通文本、商品检索结果或伪造的展示快照不能代替实际草稿观察。

## 来源与事务

`intent_contract.py` 定义严格候选和应用签发结构，来源采用 Python Unicode `[start,end)` 区间；
引号与代码按单次扫描隔离，客户、备注保留原文，未闭合边界需要澄清。字段与数量规则在
`erp_store` 共享，MCP 保留原导入入口。新模式额外检查完整业务片段，未理解内容不能被静默忽略。

`pending_intents` 是独立的元数据表，只在 `enforce` 初始化，默认有效期十分钟，
可通过 `IntentStore(ttl_seconds=...)` / 分析器构造参数配置。
待完成请求保存原始消息、展示候选、目录指纹、会话、状态版本和已保留字段；不预留库存、保存报价或进入审批。
换题、撤回、过期、目录候选或商品属性变化都不能沿用旧编号执行。
`intent_clarifications` 只记录请求/版本/真实轮次标识，供两次未解决后的表单提示使用；
重复工具调用不增加次数，接受补充后的新版本重新计数。拒绝的回复不会改写已接受请求、状态版本或延长 TTL。

`draft-intent-2` 来源通过应用通道传递，不进入模型可编辑参数。
保存事务重新解析原始多消息、重查真实目录、核对完整快照及状态版本，并与草稿同事务消费请求。
复合修改重新绑定原草稿版本，失败整体回滚。新重放版本使用独立的多消息审计格式，逐字段和逐商品记录真实来源区间；
预算与备注等后续修改的来源哈希属于实际补充回复，不冒充初始消息。
没有伪造或改写“标准用户原话”。旧来源仍可读取，新来源在回退 `off` 后仍可核对并提交已保存版本。
提交时再次复核新来源；候选请求十分钟有效期不会让已经保存的报价随之失效。

表单确认另走应用签发的 `intent-form-1`，绑定 `pending_id + state_version` 并要求完整字段。
保存事务复核会话、版本、有效期、原始来源和目录指纹；即使用户未先完成所有语言补问，也可明确核对完整表单后保存。
确认后的字段沿用 `draft-form-1` 的 `manual_form` 来源，附带原待完成请求与真实消息上下文；
不把表单编辑冒充为字面语法核验。一次保存与请求消费同事务完成，目录变化、重复确认或并发旧版本不能多建草稿。
若目录已变化，显示需要重新核对完整请求，不自动迁移旧候选。报价失败保持请求，事务插入后失败也整体回滚。

旧展示引用记录工具调用 ID、草稿 ID、版本及内容哈希。执行前和事务内都对照同会话的不可变历史版本核对，
同时要求本轮重新读取目标当前版本；旧观察不能替代本轮读取。首批重放格式和旧字面契约继续保留读取分支。
网页严格校验多消息商品来源中的消息引用、哈希格式、Unicode 区间、完整清单或版本继承关系。
每个待完成请求最多保存 102 条真实消息，达到上限要求重新核对完整请求，不能截断来源。
同一回复可同时提供选择和数量证据，网页允许每项最多 204 个来源区间，保留全部证据。
缺失件数的原始商品片段只证明商品要求，件数槽来源指向实际补充消息；同轮选择与补件数分别留证。
新请求元数据使用 `creation_slots_version=1`，保存/提交均重放原始消息，旧请求无需迁移或补造来源。

新路径按整张清单批量查询精确 SKU/名称及数字边界候选，保留真实重名总数，单名称最多取前 20 个候选。
SKU 与另一商品名称相同仍计为多个匹配，截断候选不能靠编号放行；未知商品的建议只用于提示。
单个名称保留计数加限量读取，避免对大量重名商品排序；长清单使用窗口查询。
每次分析重新读取目录，执行许可、库存、报价和审批不加入缓存。原 `off` 路径保留原查询方式。

运行时新增业务无关的工具阶段回调，同时控制可见工具与调用前检查，完整注册表继续保留。
读取任务与修改不能在同一批次绕过前置事实；短回复不允许申请提交或取消订单。

`GET /api/sessions/{id}/state` 在启用模式下返回 `pending_intent`，包括真实问题、候选、保留字段和版本。
恢复读取不消费状态、不调用模型、不修改业务表。
`GET /api/sessions/{id}/pending-intent/preview` 返回完整核对信息，
`POST /api/sessions/{id}/pending-intent/confirm` 只接受严格表单与请求版本，不接受来源、许可或提交订单参数。
确认复用会话锁，活动对话或未完成执行期间拒绝；不初始化模型。网页旧窗口遇到请求改版、过期、读取失败会禁用保存，
冲突不自动重试，保留当前编辑；切换会话清除旧编辑并忽略迟到读取。默认关闭和影子模式不开放新入口。

## 本地整轮诊断

API 在 `shadow/enforce` 下对每个已进入执行的对话和恢复执行段，在原 trace 旁追加同名前缀的
`.intent.jsonl`。没有工具调用的闲聊也记录开始与结束；状态/预览 GET 不建立执行段。
默认 `off` 不生成新诊断文件。CLI 或直接调用存储不经过 API 宿主时不自动建立整轮文件。

每行立即关闭文件，包含独立请求 ID、会话、模式、顺序及 UTC 时间；开始记录解析/策略/来源契约版本、
系统提示词哈希、执行段当前 user 消息及所有 user 消息的哈希引用。普通对话保留原话，
草稿提交确认沿用应用生成的版本确认消息；该消息不是自然语言解析的用户原话。
规则结果、未决项、影子结果、核验拒绝、
阶段工具许可、实际工具尝试/执行/结果分别记录，拒绝不抹掉尝试；最终记录实际保存的草稿版本。
没有调用规则时明确标记 `not_requested`，不把一般对话伪称为已完成订单解析。

业务模型的开始/结束和逐步 usage 按运行时事件记录，缺 usage 或开始后中断的步骤保留为未知。
`business_model_requests` 统计运行时开始事件，不替代供应商账单或 HTTP 请求审计；
未配置语义候选时没有额外意图模型请求。配置后记录 `model_billing`、意图请求数、
逐请求用途/usage/原币种估价、已知金额和未知请求数；见下一节的持久化预算协议。
普通 `LoopEnd`/逐步 usage 仍表示业务循环，不能用它们代替包含语义分析的统一账本。
恢复执行分配新诊断 ID，保留关联运行 ID；正常取消标记中断，进程退出遗留的已写前缀没有结束事件，不能算完成。
文件故障输出 `intent_diagnostics_unavailable` 并停止该段诊断，不改变工具校验、执行或草稿结果。
该本地文件沿用原 trace 的原话留证范围，不作为业务证据或授权输入。

## 显式配置创建语义候选

API 工厂的 `intent_semantic_settings` 默认 `None`。只有 `enforce` 的真实 ERP 会话工具源可配置
`mcp_erp.intent_semantic.SemanticSettings`；普通启动、`off/shadow` 和 CLI 不自动新增供应商请求。
配置需要独立 `budget_id`、已确认的 `EndpointRate`、原币种 `Decimal` 金额上限、请求次数上限和总截止时间。
API 声明的模型及客户端实际模型/端点主机必须与该费率一致；费率不可标为 `unconfirmed`。
不能把一个已配置语义预算的工具源共享给另一个 API 宿主，请为每个宿主重新创建工具源并恢复同一预算账本。

```python
from mcp_erp.intent_semantic import SemanticSettings

settings = SemanticSettings(
    rate=confirmed_rate,
    budget_id=budget_id,
    limit=approved_native_limit,  # Decimal，币种由 confirmed_rate 给出
    max_requests=request_limit,
    timeout_seconds=30,
)
app = create_app(
    session_erp_tools=provider,  # 显式 enforce
    model=confirmed_rate.model,
    intent_semantic_settings=settings,
)
```

共享规则先解析并核对真实目录；已经可处理的完整要求或待补问请求不额外请求模型。
无法覆盖的新创建表达，在已识别的否定/条件/引用/旧草稿修改屏障之外，至多请求一次候选。
例如“帮客户甲列份采购清单：机械键盘要四个，预算1500元，备注『不要提交』”。
模型只收到当前原始消息和有限 schema，不附全量历史、业务工具或执行许可。
模型输出先用严格 `QuoteCreateProposal` 校验：唯一出现的完整原文可省略起止位置，程序精确定位；
重复片段必须同时给出明确起止位置。已有位置错误、只给单边位置、外来消息和不存在的片段均拒绝，
不会自动修正或默认取第一次出现。定位结果继续通过原 `CreateProposal` 校验，持久化格式保持原严格区间。
拒绝未知字段/动作、重复 JSON 键、代码围栏、非有限数字、
布尔件数、伪造位置/消息、重叠证据、引文中的动作/商品/件数、包装换算和不存在的商品。
客户/备注保留原文；数量、金额逐一对照真实来源；商品匹配仅用实际精确名称/SKU，重名保持待选。

本档候选全部进入完整表单核对，不生成 `resolved`、`draft-intent-2` 或自动保存许可。
网页明确显示候选性质、完整原话和尚未映射为字段的原文；缺失客户/件数、重名 SKU 不自动填值。
用户可补齐或改动全部字段，点击“按此完整清单保存草稿”后才走 `intent-form-1`。
保存事务重新校验实际原话、候选结构、目录指纹、会话/版本/TTL，并与完整手工草稿同事务消费。
历史来源为 `manual_form`，附原始候选与原话，不能冒充语义模型已获得字面核验。
编号或简短补充不能确认语义表单；异步返回的旧候选不能替换更新的待完成请求。

`intent_semantic_attempts` 在请求前占用会话/真实轮次，重复工具调用或宿主重建后不重发同轮分析。
`intent_model_budgets` / `intent_model_requests` 记录固定配置和所有意图/后续业务模型请求。
复用从评测包迁出的 `agent_core.billing` 协议，`evals.billing` 保留原导入入口；原计价公式、币种和缓存上界口径不变。
两类请求使用同一客户端/费率/预算，按用途分别留证并汇总，失败和格式拒绝的请求也计量。
SDK 的 HTTP 自动重试关闭；不进行格式修复请求。无余额、次数耗尽、超时、缺失/非法 usage、
中断或未知费用会停止依赖请求；重建宿主从账本恢复已知费用和未知状态，不能通过重启清零预算。
同一 `budget_id` 的金额、币种、模型/端点、费率、次数与时限不可覆盖。
对外重新核对时不自动开启新预算；账本故障时停止依赖请求，而诊断文件故障仍只影响诊断。

P0/P1 尚不能整体验收：初始缺件数/单位的补问仍要求明确客户、已支持的创建句式和可核对的完整商品名/SKU；
客户或商品本身缺失、增删及替换商品需重新核对完整请求。
待创建请求没有草稿版本行号，不从“当前版本第几行”猜测目标。没有实际观察或历史内容已压缩丢失时，要求明确 SKU。

## 业务面板中按原话修改已有草稿

显式配置同一语义协调器后，运行信息增加 `intent_semantic_revision_enabled: true`。
用户在业务面板选择目标草稿，用“修改原话”填写要求，点击“按原话生成修改预览”。
多份草稿须先明确选择；存在未保存的表单编辑、待审批/未完成运行、过期或已提交目标时入口不可确认。
普通启动、off/shadow 及未配置语义模型的环境不增加这个入口或模型调用。

`POST /api/sessions/{id}/pending-intent/revise-preview` 接收原话、独立 `request_id` 和
明确 `target={draft_id, revision}`。这个来源是用户显式提交的面板原话，不冒充聊天运行的用户轮次。
服务端在请求前从当前会话读取目标最新版本并校验有效期，将有限基准字段作为只读数据提供给模型。
模型候选仅支持原清单唯一完整商品名/SKU 的明确最终件数，以及客户/备注/人民币预算设置；
未提供的字段及商品由程序保留，null 不自动清空已有值。
条件、提交/取消、包装换算、增删商品与旧展示/行号指代不在这个模型修改入口中猜测。
复杂要求仍可对照原话，在最终完整表单内显式编辑后核对。

候选从 `QuoteReviseProposal` 定位并通过严格 `ReviseProposal` 核验。
不允许添加原清单外商品、重复匹配或从基准复制原话证据。返回时再次核对目标未改变，且不能覆盖新待完成请求。
持久化来源包含目标版本/原快照指纹、原字段、原始候选、原话和目录指纹。
GET 恢复仍只读，界面展示目标标识/版本、原完整清单及候选完整表单。

确认沿用 `/pending-intent/confirm`，必须显式提交所见 `target`、请求版本和完整字段。
事务内重查会话、目标最新版本、原快照、原话、目录、TTL，并与同一草稿新版本的保存一起消费请求。
失败回滚；并发/重放只保存一次。创建预览不能拿来修改，修改预览也不能拿来新建或改其他草稿。
历史来源为 `manual_form`，分别保存原候选和用户最终字段；用户可在完整表单中明确清空备注或预算。
保存仍只重新报价，不提交订单、不扣库存、不申请审批。

该入口复用现有持久化共享预算、一次请求、无自动重试、缺 usage 停止的协议，未开启额外真实预算。
本批只完成脚本模型/API/SQLite/前端验证，详见[验收](../reports/acceptance/2026-11-02-intent-revision.md)。
聊天内自动目标选择和规则修改权限没有据此扩展，上一批未知费用与冻结状态保留。

## 模式切换与旧会话恢复

开启过 enforce 的数据库切回 off/shadow 时，未消费的 pending/ready 请求在写锁内改为
needs_recheck，并递增版本；原话、已接受字段和有效期保持，已保存草稿与审批记录不变。
重复启动回退模式不会重复消费或续期。回到 enforce 也不会把该旧请求重新变成可续接状态。
这一步仅处理新意图表中的待完成元数据，不改旧草稿来源、旧审批参数或订单。
原本没有意图表的旧数据库保持旧路径，不因默认 off 而建意图表。

GET 预览与会话恢复可只读展示“需重新核对”，can_confirm=false，不提供继续保存的权限。
关闭模式的 POST 确认仍拒绝；旧候选编号、件数、预算短回复和简短确认由程序只读结束，
不调用模型、不申请审批、不借用旧候选。完整新请求产生新的请求标识，不能使用旧确认版本。
新请求消费后，旧停用提示不会重新浮现。

真实 PostgreSQL 断开连接并重建宿主/连接池的三模式矩阵，保留旧 pending_id、参数和 expires_at，
批准与拒绝分别核对实际订单和库存。draft-intent-2 已保存草稿在 off/shadow/enforce 下仍可核对与提交。
原有进程硬退出和恢复专项也使用隔离 PostgreSQL 执行，不再因缺配置跳过。
完整证据及环境清理见[恢复验收](../reports/acceptance/2026-11-02-intent-mode-recovery.md)。

人工复核包位于 [120 例核对表](../reports/review/20261102-intent-core/review.md)，原冻结数据未修改。
用户本轮明确选择暂未复核，继续保留工程预期标签；默认仍 off。
真实创建新批次首笔推理连接失败、缺 usage 后停止，修改新批次未启动，没有通过重建账本绕开未知费用。

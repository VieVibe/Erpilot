# 核对指定草稿版本并申请审批

日期：2026-10-21。承接[完整订单任务验收](whole-order-acceptance.md)中“外部改稿后，笼统确认仍可能被模型追问”的问题，新增明确的网页操作入口。

## 用户操作

1. 在业务面板选择草稿，保存所有编辑，点击“请求提交版本 N 并审批”。
2. 在核对窗口查看完整客户、备注、全部商品、数量、原价、折扣、成交单价、小计、总金额及有效期。手机端逐项展示。
3. 点击“确认此版本并申请审批”，申请的是核对窗口打开时的版本。取消窗口不会发送提交请求。
4. 独立审批卡出现后，再选择批准或拒绝。批准前不建单、不扣库存；批准后仍复核版本、报价、库存与商品状态。

草稿变化、失效、尚未保存或已有待处理操作时，不能继续确认。服务端发现版本变化返回冲突，网页刷新当前草稿，等待重新核对；不会替用户改成最新版本重提。审批期间条件变化仍按原业务错误终止本轮，刷新报价后需要新的确认和审批。

## 执行契约

`POST /api/sessions/{session_id}/order-drafts/{draft_id}/confirm/stream`

请求仅接受 `{"expected_revision": N}`，N 为严格正整数；拒绝额外字段。服务端核对会话归属、写入能力、最新未提交版本及未完成任务，并持有现有单进程会话锁。

宿主生成 `application-confirmation-*` 调用，绑定不可变 `draft_id` / `revision`，经正式 LangGraph → HITL → MCP → ERP 链路执行。工具调用由明确的人类页面操作选择，不能归功于模型自主理解。请求不接受客户端传入商品、金额、批准状态或幂等键。

新入口的 SSE `start.execution_mode` 为 `confirmed_action`。检查点保存执行模式；初次申请、批准后的续跑和结果展示均不请求模型，模型客户端也不会因读取状态而初始化。完成事件的 `usage` / `cost` 保持 `null`，不伪造 token 计量。普通聊天入口维持模型驱动。

复用现有审批身份、工具版本 / 参数指纹、幂等键、写前复核与对账机制。成功文案从实际批准后的 ERP 订单结果生成；已知拒绝和失效错误使用既有终止说明；结果不确定时仍进入对账，不能用页面确认代替成功事实。

运行时仅允许具有审批风险和可信结果渲染器的工具通过该入口；本批只为 `submit_order_draft` 装配。没有新增通用“直接运行任意工具”HTTP 接口，也没有数据库结构迁移。

## 验证与范围

见[本批验收](../reports/acceptance/2026-10-21-draft-confirmation.md)。新增 API 测试将模型工厂设为一经初始化即报错，验证批准 / 拒绝、旧版本、跨会话、重复请求、报价变化及恢复。浏览器覆盖 320 / 1440px、取消核对、版本冲突及备注按纯文本显示；本地正式 API 演示覆盖拒绝后从该入口重新确认并批准。

恢复测试重建宿主并共享 `InMemorySaver`，包括同幂等键已提交的受控夹具，不等于新一轮真实进程硬退出验收。运行范围仍为本机可信单用户、单 API 进程。

原自然语言三流程 GLM **2/3** 保留；此前明确接受外部变更的独立流程仍单列。本批没有新增付费模型调用，未证明两模型共同完整验收，也不解除 DeepSeek 未知 usage 的冻结。当前新入口解决的是用户明确选择并核对版本后的执行确定性。

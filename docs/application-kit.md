# Erpilot 求职投递材料

定位：Agent 应用开发 / Python 后端工程作品。业务场景为 mini-ERP 的商品、库存、订单；
模型通过 MCP 查询事实、保存草稿与提出操作，业务层和人工审批决定是否执行。

## 可直接使用的项目描述

**Erpilot｜审批型 ERP 智能体**

Python、FastAPI、LangGraph、FastMCP、SQLite、PostgreSQL checkpoint、React / TypeScript。

- 实现报价草稿、多轮修改、固定版本人工审批与订单提交；事务内复核价格、库存和版本，
  稳定幂等键防止重复业务提交，支持流式工具时间线、断线恢复和历史会话。
- 实现商品名称与规范中文件数的只读核对及歧义澄清，将完整要求绑定 SKU 清单；保存事务
  重查名称与数量，原话及映射随版本留证。新输入功能的验收为离线工程范围。
- 实现政策检索、有效版本筛选、本轮引用绑定、原文 / 哈希校验和程序渲染；建立冻结用例、
  两模型对照、逐轮数据库验证、未知用量熔断和可中断评测。受阻检索由程序直接结束；
  最新独立 GLM 政策 v4 在十三条受控检索用例中 13/13，旧 v3 两模型各 11/13 保留。
- 实现可选上下文投影并比较信息保留与真实 token；历史快照实验中输入 token 相对原策略
  减少约 62%，候选答题 GLM 8/10、DeepSeek 9/10。新增连续多轮真实业务验收，结果与
  快照实验分列，详见[连续多轮上下文验收](context-workflow.md)。

这些是仓库可验证的实现描述。求职者应按本人实际参与范围修改“负责 / 独立完成”等措辞。
项目没有测量企业节省人力、订单转化或生产吞吐，不填写推算的业务收益。

## 三个技术取舍

| 话题 | 可以这样解释 | 证据 |
|---|---|---|
| 审批、版本与幂等 | 模型提出操作；批准绑定具体版本，执行时再次校验。幂等解决重复提交，条件变化则重新确认 | [订单案例](interview-cases.md)、[恢复边界](write-reliability.md) |
| RAG 来源与回答 | 命中与充分性分别验证；程序从本轮取证并复制原文，受阻后直接结束；问题与证据的语义选择仍可能失败 | [检索对照](retrieval-experiment.md)、[GLM 新批次与旧结果边界](../reports/acceptance/2026-10-28-contracts-and-policy.md) |
| 上下文与状态 | 业务状态存数据库；请求视图保留用户原话、最新任务快照和工具配对，超过估算预算时停止。摘要仍有事实时效和字段边界 | [连续业务任务](context-workflow.md)、[历史快照实验](context-experiment.md) |

每个话题按“具体故障 → 为什么这样设计 → 怎么测 → 尚有什么边界”讲解。
历史崩溃恢复的 19 项进程测试是独立验收记录，本轮没有重跑；视频中的刷新只覆盖进程内恢复。

## 面试前自行演练

1. 用五分钟解释一次请求如何经过 SSE、LangGraph、MCP、事务校验与审批，再定位相应源码。
2. 解释为什么草稿库存不是实时库存，为什么审批和幂等都不能省略。
3. 选一份失败报告，从用户原话、工具请求、数据库差异到费用日志，复述定位过程。
4. 解释上下文输入减少与完整任务成功率的区别，以及为何候选策略继续显式启用。
5. 说明当前单用户、单进程范围；身份认证、多租户和多 worker 执行权仍需独立设计。

投递时附仓库地址或交付 ZIP、演示视频及本材料。真实岗位要求、个人经历、联系方式和公开发布
由本人核对；本轮交付为本地材料和源码快照。

## 正式链路的改动

用户本轮明确说“查询 / 查看 / 读取草稿 `<32 位十六进制 ID>` 的修改记录 / 历史记录 / 版本历史”时，
应用先通过正式 MCP 读取该 ID，再请求模型作答。查询结果可以是实际记录、`not_found` 或其他失败；
不能用当前未提交任务列表代替该目标查询。用户明确要求“先查询当前任务”时，先完成任务查询再读取历史，
不会并行绕过顺序。明确的 `limit=` / “每页”及 `before_revision=` 采用用户给定参数，由工具校验范围。

这是有界的明确目标路由，不是通用自然语言理解。只读取最新 user 消息中的查询分句；
引号备注内的同形文字和旧聊天不能触发读取。没有明确 ID 的请求仍由模型查询 / 澄清。
历史原话只作为数据，不触发旧修改或建单。一次目标查询失败后不自动回放。
其他语言、复杂否定或间接指代不作同等路由承诺。

前置读取由应用选择，不伪装为模型自主选工具：调用 ID 以 `application-read-` 开头，
进入正式工具事件、模型上下文和检查点；不计为供应商请求或模型步骤，不生成 usage。
通用运行时只支持装配在无审批风险工具上的读取回调，本次仅绑定两个只读查询工具，
并将消息及工具历史深拷贝给回调。该机制不改变写操作的审批路径。

`revise_order_draft_quantity` 的公开 MCP 参数 `expected_sku` 现在必填，调用方须升级。
应用同时要求本轮已读取同一草稿及版本、行号有效、该行 SKU 与参数一致；
版本 / 行号 / 数量等参数不将布尔值或数字字符串强制转换后接受。MCP 和领域层继续校验
会话、最新版本、SKU、库存与报价。可信 Python 集成原有可选参数保留兼容，不代表模型可省略。

普通草稿输出新增 `item_count` 及 `items[].item_number`（从 1 起算），由真实明细计算。
创建、修改、查询、列表、任务恢复的响应保持一致；结构化上下文摘要也保留总行数。
这些展示字段不改写旧快照，不新增数据库表或列。指引要求模型使用返回事实，不自行估算行数。

完整流程实测发现模型在提交受阻后仍可能自行修改或刷新草稿，已增加应用装配的终止规则：
指定版本、报价、库存复核失败或审批被拒绝 / 取消 / 过期时，程序直接输出固定业务说明并结束本轮，
不再请求模型，不自动修改、刷新或重提。尚未执行的同批写调用标记取消，保留完整工具配对和事件。
下一轮用户明确要求刷新后才生成新报价，再由新确认和审批决定提交。
终止规则由可信工具元数据装配，不接受模型或工具结果自行定义；结果不确定时保留原对账 / 恢复路径。

## 三条固定流程

| 流程 | 阶段数 | 检验内容 |
|---|---:|---|
| selection-and-denial | 10 | 从用户请求创建两份草稿；目标不明时澄清；选择甲连续修改两行；等待审批、拒绝、重新确认后批准；核对最终答复 |
| approval-drift | 11 | 创建后等待审批；明确外部表单编辑使旧批准版本失效；重新确认后外部价格变化使报价失效；刷新但不提交；重新确认并批准；核对最终答复 |
| restore-pending | 7 | 创建、修改、等待审批；重建运行时和会话工具工厂，恢复同一待审批对象；批准；重复旧决定被拒绝；核对最终答复 |

共 28 个受控阶段，其中模型请求、审批决定及外部动作分列；“28 阶段”不是 28 轮模型问答。
真实验收中，模型可能对外部修改后的笼统“确认当前版本”要求再次核对，原固定用例仍保留失败。
另设独立 `whole-order-explicit-1` 范围，明确给出用户接受的版本、数量与金额，验证真实确认后能继续
完成条件变化流程；它不覆盖或替换原三用例，不把不同确认文字下的结果合成为统一成功率。
每条流程创建独立合成商品库，正式 LangGraph / FastMCP 执行，逐阶段保存全表前后状态与 trace。
客户甲 / 乙的初始两行数量 2 / 3 均由用户请求、工具和所选模型产生，不预置成功草稿。
初始其他会话草稿用于隔离检查，属于明确夹具。

审批决定由验收脚本扮演人类给出；外部表单 / 价格变化是明确控制动作，不能归功于模型。
恢复项重建宿主对象并共享同一个 `InMemorySaver`，验证对象恢复和审批身份；
不等同于真实进程退出后的持久恢复。既有 PostgreSQL / 硬崩溃矩阵不在本轮重新验收范围。

## 判分和证据

每阶段核对准确的草稿版本数、全部商品顺序和数量、客户 / 备注及其原来源、旧快照不可变、
其他客户和会话不变；只有明确批准后才允许恰好一张绑定订单和准确扣库存。
订单单价另用正式计价契约检查，旧批准或旧报价必须返回对应错误，不能静默改版再提交。
阶段出现非预期修改工具请求，即使未执行也失败；原批准版本和恢复后 pending_id 必须匹配。
最后一轮要求实际读取目标，并严格核对可见 JSON 的客户、备注、数量、金额、状态和订单号。

失败即停止后续依赖阶段，不重跑失败场景；SDK 重试为 0，单请求截止 60 秒。
未知用量冻结对应模型后续调用，其他模型独立计量。报告列完整 / 通过流程、已执行 / 计划阶段、
原币种估价、未知请求、冻结源码与范围哈希。独立离线审计重算请求计量并从前后全表重判各阶段，
“记录一致”与“流程成功”分别报告。

本套显式采用 `structured` 上下文候选及原压力策略（消息估算 6000 token、最近 8 条、工具 8000 字符），
不切换 API / CLI 默认上下文策略。全历史保留与预算边界继续遵守[连续任务契约](context-workflow.md)。

普通 pytest 使用脚本模型，绝不调用付费端点；真实模型使用独立批次：

```powershell
.venv/Scripts/python.exe -m evals.order_journey --model glm-5.3-flash --budget 0.10 --budget-currency CNY --output reports/context/new-whole-order-glm
.venv/Scripts/python.exe scripts/validate_draft_history_live.py --previous reports/context/new-whole-order-glm.json --output reports/context/new-history-glm
.venv/Scripts/python.exe scripts/audit_order_live.py reports/context/new-whole-order-glm.json reports/context/new-history-glm.json --output reports/context/new-whole-order-audit.json
```

历史专项只使用该模型新批次剩余且计量完整的预算；旧未知费用、失败与预算保持独立。
历史脚本 v2 修正了中断时的答复记录：没有完成的助手答复记为空，不能把初始系统消息当作模型最终回答。
旧 v1 原始报告不回写；其受影响字段不得用于可见答复的结论，实际请求和错误记录仍有效。
预算是按现有端点费率的估价熔断，不是供应商账单或硬上限；真实表现以独立验收报告为准。

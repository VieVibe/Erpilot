# 按商品名称与中文件数下单

2026-10-28。对话可以将完整商品名称及中文件数核对为 SKU 清单，再保存报价草稿。
保存后核对完整商品、数量、金额、预算及版本，继续使用既有人工审批建单。

## 可以怎样说

商品目录中确有对应商品时：

> 给客户甲准备订单：无线鼠标两件，三件机械键盘；备注原文「分箱发货」；预算上限为1000元；只保存草稿

也支持原有“保存报价草稿：…”的句式，商品可混用完整名称和明确 SKU。中文件数支持
“两、十二、一百零二、两百、两千零二”等规范写法，范围 1–9999；阿拉伯数字范围为
1–999999999。单位当前为“件”；一百二、一千一、若干、分数、箱 / 包 / 重量等先澄清。

已有草稿先查当前版本后，可以说：

> 把商品无线鼠标数量改为三件，其他不变

> 把当前版本第一行改成三件，其他不变

同一草稿有两个同名商品时，用明确 SKU 或行号选择；修改保留其他商品、客户、备注和预算。

## 名称不明确时

完整名称或明确 SKU 必须对应唯一商品。名称重名会展示实际候选的名称、SKU 和状态；
简称即使只搜到一个候选也需要用户明确完整名称或 SKU。下架商品不自动替换，重复商品
不自动合并，件数和名称末尾数字有多种解释时请把件数放在名称前，例如“十二件维生素B”。

澄清后的回复需重新提供本次完整要求：客户、商品、件数，以及需要保留的备注和预算。
这是尚未保存的请求；“就第一个”“按刚才的来”等短回复不会直接授权创建。也可以在
草稿表单逐项核对。已经保存的草稿修改继续继承其实际客户、备注和预算。

## 可信执行路径

1. 应用对名称 / 中文件数请求先执行无参数只读工具 `resolve_order_items`，绑定真实本轮原话；
   模型不能改写来源，也不能传入另一份清单。读取不保存、不预留库存、不申请审批。
2. `resolved` 给出完整有序 SKU / 件数，模型只能按该清单创建；任何漏项、多项、错量或
   错序在保存前被拒。`clarification_required` 不返回可执行的部分清单。
3. 保存事务内重新解析原话并核对当前目录；名称变化、出现新重名或商品下架时停止保存。
   名称映射与原话、件数和版本原子留证，`item_constraint` 区分目录解析与原始 SKU 清单。
4. 网页可展开“查看原始商品要求”，逐项显示原话、实际商品、SKU 与件数；手机可滚动核对。
   核对后仍需指定版本审批，执行时复核报价、库存及幂等。

引文、备注、代码、旧消息、条件、否定和可选数量不提供当前创建授权。商品名称中的文字
只作数据。此功能是有限句式与明确件数的业务契约，不是任意自然语言理解或单位换算。

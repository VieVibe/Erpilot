## 初次创建的商品要求

对话创建草稿必须在本轮提供完整、明确的商品清单，例如：

> 给完整客户保存报价草稿：A1001 2件，B2001 3件，按此顺序；备注原文「分箱发货」。只存草稿，不提交。

支持 SKU、阿拉伯数字正整数件数、逗号 / 顿号 / 分号分隔及明确顺序；同一 SKU 只列一次。
模型参数按领域层的 SKU 去空白与合并口径核对完整有序明细。
漏项、额外商品、替换、错误件数或顺序会在调用保存工具前被拒绝，不产生错误草稿版本。
条件、否定、二选一、中文数量、缺少完整清单或不支持的表达先澄清，或通过草稿表单核对。
备注、普通引用、代码、旧用户消息和助手消息不能提供本轮商品授权。

这仍是有限明确格式检查，不是通用自然语言语义证明。客户、备注与预算继续沿用各自的有限格式契约。
同一轮可以根据错误纠正模型参数；建单仍需要固定版本核对与人工审批。

应用生成 `creation_guard`（`draft-create-items-1`），模型参数不能提交该证据。
领域层在保存事务内复核实际明细、逐项数量与原话引用；证据随版本原子进入 `change_record.creation_guard`。
独立 `item_constraint` 保存当前完整明细、核验状态和来源；不改变原有 `task_constraints.fields` 的客户 / 备注结构。
明确创建或表单核对后，`items` 从 `unverified_fields` 移除；后续经过商品变更检查的修改延续核验状态。
没有初始核验的旧草稿，即使本次修改通过，也不追溯认证其最初商品选择；旧记录不补造来源。
原始独立 MCP / 可信 Python 调用没有真实对话来源，仍可创建未核验来源的草稿；该边界不是身份认证。

## 待确认事项与提交检查

读取草稿时，后端以当前业务数据计算 `pending_issues`，保留原报价快照：

| 事项 | 处理 |
|---|---|
| 预算超额 | 展示原预算、报价及差额；等待明确调整预算或商品，保存新版本 |
| 报价过期 | 明确刷新报价，再核对新版本并审批 |
| 已有新版本 | 读取当前版本；旧确认不能授权新版本 |
| 商品不存在 / 下架 | 明确处理商品，不能静默替换或删除 |
| 名称、现价或折扣变化 | 明确刷新报价，不静默用新价格建单 |
| 库存变化 / 不足 | 展示当前件数及需求，等待明确刷新或修改 |
| 多份未提交草稿 | 任务查询返回选单事项，用户明确唯一客户或草稿标识后再操作 |

每份草稿的事项绑定具体版本、阻塞状态与处理方式。`submission_check` 记录检查时间、当前版本和能否申请提交。
它是读取时的观察，不预留库存或锁价。历史版本的报价与预算不因检查被重写。
无法解析的创建需求不保存草稿，而是返回澄清信息；没有自动创建代表“已确认要求”的记录。

网页展示所有事项及检查时间，禁用受阻版本的提交 / 批准；同版本收到新检查结果时，已打开的核对窗口也停止确认。
多草稿时先明确选择目标。旧服务没有新字段时仍按原有效期与预算显示。
专用确认接口与模型申请审批前重新检查当前事实，实际提交在原写事务内再次检查。
审批后业务条件变化仍会停止，不能以先前 `can_submit=true` 绕过事务复核。
已提交订单保留原幂等结果，不因之后库存变化重新执行。

## 独立完整任务评测

新增 `python -m evals.order_reliability`，版本 `order-reliability-1`：四流程、34 个受控阶段，
覆盖预算受阻与明确提高预算、审批拒绝 / 恢复、现价变化及刷新、多草稿澄清与指定修改、
旧审批失效、重复决定和最终实际订单查询。旧 B4、订单、预算用例及评分器不改判。

每阶段保存完整工具历史、回答、全表前后快照及哈希、耗时、指定版本和批准对象。
整单核对所有明细、预算、旧快照、其他会话、精确库存和唯一订单，不只检查最终回答。
失败后停止当前任务；报告仍保留全部计划任务 / 阶段的分母。沿用原币种预算、零自动重试、未知 usage 熔断及独立请求日志。

本批只执行脚本模型及临时库验证，包括“首次提错件数 → 拦截且全表不变 → 纠正 → 只保存正确 v1”。
脚本模型的模拟 usage 只验证计量接线，不是供应商消耗或模型成功率。
本批没有付费模型 / 嵌入调用，不重开已跳过或冻结的 DeepSeek 批次，也不改写原真实模型结果。

专项入口：

```powershell

```

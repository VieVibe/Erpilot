# 草稿商品变更的保存前核验

日期：2026-10-22。沿用多轮订单可靠性主线，补上已有草稿的商品数量变更检查。

2026-10-28 后续增加[自然商品输入](natural-order-entry.md)，当前已查询草稿支持“把商品无线鼠标数量改为三件”及中文行数量；同名需明确 SKU / 行号。新创建的名称映射先核对目录并在保存事务复核，本页保留原阶段范围及历史结果。

后续更新（2026-10-27）：[P0 / P1 创建核验与待确认事项](order-reliability-p0-p1.md)已补首次创建的完整明确清单检查及独立商品来源。本页保留 10-22 的变更契约与当时边界；旧记录不追溯认证。

## 用户可见行为

刷新报价、修改客户、备注或预算时，所有原有商品的顺序与数量必须保持。
模型不能顺便减量、删除商品或替换商品来满足预算。参数不符合本轮明确要求时，
返回 `argument_constraint`，不调用保存工具、不新增错误版本、不改变库存。
模型可以在同一轮读取错误后纠正参数；建单仍需要原有指定版本核对和人工审批。

支持的明确表达包括：

- `把当前版本第二行改成5件`、`将当前版本第31行改为77`。
- `SKU A1001 数量改为5件`。
- `按当前版本的第二行，把数量改成50件`。
- `我确认修改上一轮展示的 SKU A1001，数量改成50件`。
- 只有一行商品时，可以说 `数量改成3件，其他不变`；多行必须明确目标。
- `在当前草稿新增商品 A1002 1件，放在第二行`：只支持末尾追加，SKU 与数量之间须有空格。
  省略位置表示追加末行；原商品全部保留。

多个明确数量要求可以通过完整修改一次保存；未点名的行保持当前数量。
同一 SKU 的冲突数量、指定数量没有落入参数、附带修改其他行均拒绝保存。
删除商品、插入中间或调整顺序通过现有草稿表单核对修改。

备注、普通引文和代码片段中的指令不作为商品修改依据，旧用户消息和助手消息也不能授权。
已识别的条件、否定、只读、待确认和二选一表达要求澄清；不能只采纳其中看似可执行的子句。
可识别但未支持的行号 / 数量变更表达也会拒绝，防止保存部分修改。

## 执行与留证

1. 应用回调只读取最近一条真实用户消息，以及本轮实际查询到的相同草稿和版本。
   数量专用工具继续核对行号与 `expected_sku`。
2. 有限解析取得目标与整数数量，在当前完整明细上计算允许的结果；
   与模型参数按领域层的 SKU 规范化及合并口径比较，商品顺序也参与核对。
3. 生成独立的 `item_guard`，契约为 `draft-items-1`。它包含目标草稿、读取版本、
   前后有序的 SKU / 数量明细，以及每项要求对应的用户原话片段。
   模型工具参数不增加这个字段。
4. 领域层在保存事务内再次核对真实前后快照、版本、要求数量和原话引用，
   拒绝伪造快照、未授权追加或夹带变更；记录随版本原子写入 `change_record.item_guard`。
   报价刷新可以改变现价、折扣或预计库存，但不能改变用户商品要求。
5. 历史接口保留这份检查记录和原有实际差异，重建工具实例后仍可查询。
   旧记录不补造检查证明，普通草稿读取不重复携带整份历史。

没有新增数据库表或列，没有修改原审批、预算、计价和幂等协议。

## 边界

这是有限格式检查，不是通用自然语言理解或语义证明。行号取自本轮当前版本；
未限定版本的行号与旧展示顺序发生歧义时，仍按原 B4 契约先澄清，不能宣称新增了通用指代判断。
SKU 明确表达支持英文字母、数字、连字符、下划线和点；数量是正整数，
中文数量、相对增减、任意条件与自由改写需要澄清或表单。

创建草稿的商品需求尚未核对用户原话；`task_constraints.unverified_fields` 继续保留 `items`。
这份记录只说明本次已有草稿的变更符合所支持的要求，不会追溯认证初始商品选择。

原始独立 MCP 和可信 Python 调用没有真实对话来源，仍沿用原行为；没有附带 `item_guard`
的旧集成不会自动获得商品授权检查。手工表单继续明确编辑完整商品。
该机制属于应用执行契约，不是身份认证或防止可信调用方修改程序的权限边界。
